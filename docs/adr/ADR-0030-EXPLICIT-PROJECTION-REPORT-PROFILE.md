# ADR-0030: Explicit projection and goal report profile four

Status: Accepted design for implementation. Runtime integration and acceptance evidence remain pending.

## Context

ADR-0026 froze the meanings and bytes of report profiles one, two and three. Projection and goal families remain unsupported by those profiles. The retained projection pipeline now has immutable assumption/goal versions, a full capture digest distinct from its numerical input digest, complete saved paths and summaries, and original source evidence authorized independently of a caller-supplied source UUID.

A modeled starting value has an explicit calendar date but has no observed valuation instant. Provider-only calibration evidence has a first-observed time, not a declared historical knowledge cutoff. Report-context snapshot selection is independently meaningful and must not invent those missing original clocks.

## Decision

Introduce an explicitly selected `report_sections_v4` / document `4.0.0` profile. Its singular `premium_run` is exactly a `ReportProjectionRunSelection(run_id, family=projection)`. The projection section is mandatory; the goal section is optional and requires that the same saved projection run actually pins a goal version. All saved goal definition, schedule and result proof remains captured even when the presentation goal section is absent. Mixed premium runs, risk/scenario pins in this profile, research, and arbitrary input/calibration arrays are rejected.

Ordinary sections continue to use their established report selection rules. The selected owner/account report-context snapshot, its actual valuation and requested knowledge cutoff remain required. They identify the ordinary report context, not an observed projection source. A distinct binding records the actual projection root/run, input row, result row, full capture digest, numerical input digest, result digest, immutable assumption and optional goal aggregate/version/digest/metadata, original source snapshot when one exists, model anchor/terminal dates, counts and original source cutoff. The original source snapshot may differ from the report-context snapshot. No money is converted or relabeled: projection currency is the run's exact reporting currency and original source proof keeps its stored currencies.

The profile has its own `ReportContextV4`, `ReportProofV4`, header, capture and manifest types and explicit codecs. Only projection and goal contexts permit nullable original valuation/cutoff times. Ordinary contexts in profile four still require actual instants. A modeled anchor remains a date. An absent original cutoff stays null; provider first-observed time stays separately attributable and never substitutes for cutoff. The established projection provenance rule applies: overall cutoff is the maximum explicit source cutoff only when every selected source supplies one, otherwise null; empty evidence also yields null. Modeled result quality remains at least estimated.

Old `ReportContext` construction and profile-one/two/three decoders retain their old types and clock requirements. Existing selection/header/capture/manifest bytes, column schemas, field omission, scalar encoding and renderer profile remain unchanged. Shared table enums gain additive closed members; old document/profile validation explicitly rejects the new tables and proof relations. Profile-four context promotion copies ordinary source clocks without reinterpretation.

## Complete bounded table projection

The fixed registry has 24 tables, all required as descriptors, including empty proof and absent-goal tables: basis; immutable definitions; assumptions; assets including the explicit canonical initial allocation; full correlation matrix; original calendar boundaries and retained-point membership; run/goal schedules; sensitivity; variants; paths; checkpoints; checkpoint asset values; distributions; quantiles; histograms; histogram bins; goal presence; goal definition; goal results; numerical/calibration memberships; original source headers; source nodes; source memberships; source scalars.

Every saved variant, absolute path index and retained checkpoint is copied. Checkpoints include all 12 canonical monetary fields, asset values and both funding flags. Saved distribution means/quantiles, histogram extrema/bins/boundary rule, goal successes/probability/Wilson bounds/objective metadata/shortfall summaries and numerical-zero pivots are retained exactly. Initial allocation has its own retained identity and ordinal columns; the frozen numerical contract still requires its weights to equal the immutable assumption weights. Run dates map through the saved calendar without shifting dates. No random generator, path resampling, formula recomputation, forecast improvement, automatic goal acceptance or public-preview truncation is involved. Public-only derived summaries are not substituted for canonical saved financial records.

Original source trees use exactly four admitted source kinds: portfolio snapshot, canonical historical input, provider total-return price snapshot, and provider total-return benchmark snapshot. Each kind has a closed set of source-part roots validated by the retained source presentation resolver. Tables encode explicit object/array nodes, ordered membership, primitive scalar kinds, nulls and empty containers. This is an encoding of those validated retained proof parts, not an arbitrary public schema walker or new source registration API. No JSON document is placed in a report cell.

Historical `canonical_input` is special: the original document string is decoded with the existing strict historical codec, checked against its canonical bytes, emitted as structured source nodes, and accompanied by the SHA-256 of the original document bytes. Reassembling its canonical document string and the other source parts reproduces the original outer proof bytes and digest. Other source scalar strings retain their exact spelling. The complete original source proof includes metadata, original observations and gaps, source series, mapping candidates, calendars/sessions and pinned license documents. Headers separately retain original creation/physical expiration, effective authorized copy deadline, declared cutoff and provider first-observed time.

Existing report bounds remain unchanged: 32 MiB complete document, 2 MiB manifest, 100,000 rows per table, 64 columns, 4,096 characters per scalar text, 256 distinct licenses, and existing chunk/artifact/aggregate/PDF page limits. Complete source proof and saved input/result bytes are checked before emission; source-tree counts are admitted before expanded table construction. Unsupported scalars, unknown source parts, excessive complete proof or any oversized table fail closed with input-bound errors. Nothing is truncated or silently summarized to fit. Supported projection runs can exceed report quotas and remain usable as projections while their complete report request fails explicitly.

## Authorization and lifetime

The report loader acquires existing shared owner locks in sources, X-ray, historical, premium order and reads only owned permanent run/job/result metadata before private decoding. It requires the actual immutable succeeded sealed projection and report currency, retention eligibility, and bounded original license inventory. A report-specialized source resolver adds current and pinned REPORT to all existing STORE/DISPLAY and original creation/physical-lifetime checks, including calibration definition resolution, input reload, source proof and result/chunk verification. A UUID/digest pair is never authority. The same source boundary and current principal authorization run again after table capture. Existing root creation time remains the copy retention origin; report reads cannot refresh old sources.

Report lifetime is clamped to the actual projection root and all upstream effective original/source deadlines. Subsequent download/render authorization and normalized dependency guards must enforce the same retained-source checks before financial bytes and again at completion. Projection-dependent report copies and artifacts must be physically purged before upstream projection/source cleanup can complete, using the existing shared budget and lock ordering. A profile-four report cannot be admitted merely by adding the pure capture function.

## Integration boundary and validation

This proposal stages the domain/capture adapter, narrow shared hooks, and regression sources. The parent integration must explicitly compose profile-four builder/proof accumulation, ordinary context stamping, header/capture/manifest dispatch, normalized dependency metadata/migration/retention, the existing six premium REST routes and their profile-isolated lists/idempotency/cancel/status/grants, generated client, report worker/renderers and authenticated report UI. Existing routes/defaults/profile collections must remain unchanged when four is not explicitly selected. Renderers must display unavailable original clocks truthfully while retaining the separate ordinary snapshot context.

Required evidence includes strict codec/closed-vocabulary failures, old byte oracles, all-variant checkpoint/goal parity, historical proof reconstruction beyond one scalar's limit, foreign identity and source denial before private decode, expired current/original source denial, account/profile isolation, concurrent retention/worker behavior and real four-format downloads with exact numerical/proof parity. Tests in this stage are written but unexecuted; no runtime or acceptance result is claimed.
